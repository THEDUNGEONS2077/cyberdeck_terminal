# Architecture

## Layers
| Folder | What | May import |
|---|---|---|
| `src/lib/` | Pure rules: the layout document, migrations, backup files, snapshot keeping, the reminder | nothing outside `lib` |
| `src/store/` | State and storage: `persist.ts` (startup), `layout.ts` (layout store), `ui.ts` (screen state), `idbKV.ts` / `kv.ts` (storage) | `lib` |
| `src/wallpaper/` | Animated wallpapers on a canvas: `host.ts` owns the canvas and runs the wallpaper in `worker.ts`; `catalog.ts` names them, `registry.ts` holds their engines | `lib` (ids and glow levels only) |
| `src/bridge/` | `client.ts`: messaging with the bridge extension (Chrome's externally_connectable API) | `lib` |
| `bridge/` | The **CYBERDECK BRIDGE** extension itself (MV3, plain JS), zipped into the build as `cyberdeck-bridge.zip` | nothing |
| `src/app/` | React UI: `App`, `Hud`, `SystemPanel`, `Dialog`, `Toast`, `PopupMenu`, shortcuts, fullscreen; the deck in `Bookmarks.tsx` + `deck/`; `arrangeDrag.ts`, `panels.tsx`; the modules in `modules/` | everything |

## Palettes
- **`src/lib/palettes.ts`** (pure): the palettes, each a set of base colours keyed by token (`PALETTE_TOKENS`), plus WCAG contrast maths for the test that holds every palette to the colour rule.
- **Two palettes, chosen apart:** the dashboard's (`prefs.palette`) and the wallpaper's (`prefs.wallpaperPalette`; a layout from before 0.6.1 starts it from the dashboard's).
- **`src/palette.ts`** puts the dashboard's palette on the page: it sets the base tokens on `<html>` (inline custom properties) and remembers the choice in localStorage (`cyberdeck_terminal:palette`), so `main.tsx` can apply it before the wallpaper reads the colours, and a non-default palette never flashes green first.
- **`src/scale.ts`** puts the dashboard's sizes on the page (0.17.0; the rules in `lib/scale.ts`): `--ui-zoom` (the CSS `zoom` of `#root`, so everything but the wallpaper), `--text-scale` and `--module-scale` on `<html>`, plus a start-up hint (`cyberdeck_terminal:sizes`) so the UI never draws at the wrong size first.
  - **Why it cancels Chrome's zoom:** Chrome keeps one zoom per site, and quest_log_desktop shares this one, so zooming either zooms both; no page can set or refuse that zoom. `lib/scale.ts` `browserZoom` works it out (outer ÷ inner width, roughly; the pixel ratio, exactly, as zoom × an OS display scale), and with CHROME ZOOM ▸ IGNORE the UI is drawn at UI SCALE ÷ that zoom. It's worked out again on every resize (a zoom resizes the page).
  - **Inside the zoom:** Chrome zooms `vw`/`vh` too, so app.css uses `--view-w`/`--view-h` (the window in the UI's own px). Screen boxes (`getBoundingClientRect`, the pointer) are screen px: code turning one into a CSS length divides by `uiZoomNow()` (the ⋯ menus, the deck's glide, the drag label; `scaleOf` for kept widths). Shares of the window (a panel's place) need nothing.
- **theme.css** mixes every other colour from the base tokens (`color-mix`), so a palette recolours everything.
- **The wallpaper's palette** is the host's (`setWallpaperColors`): it sets the same base tokens on the `.wallpaper` element itself, so the wallpaper's CSS layers (which use only base tokens, mixed in place) take its colours while the page keeps the dashboard's; it sends the colours to the engine, and keeps its own start-up hint (`cyberdeck_terminal:wallpaper-palette`).
- Both are in the layout (no schema bump: missing ones get PHOSPHOR, or the dashboard's), so backups and snapshots keep them.

## Service worker
`sw.js` is generated by `vite.config.ts`.
- **The page is served from its cache**: no network round trip before it can start.
- **The browser checks `sw.js` on every open.** A new build installs in the background, fetching every file with `cache: 'reload'` so it never stores a stale copy, and shows from the next open.
- **The previous build's cache is kept**, so a page still open on it can load its remaining chunks.
- **Cache names** are `cyberdeck_terminal-<build time>-<hash>`, so they sort by age.

## Startup
`index.html` holds the wallpaper's canvas as plain HTML, and lists every file the start needs (fonts, the first chunks, and the app's chunk as a `modulepreload`), so they're all fetched at once.
1. `src/main.tsx`, the first chunk (about 1 KB, plus the host's, about 100 KB since the worker inlined in it carries every wallpaper's engine; 0.18.0 build), starts the wallpaper at once: `wallpaper/host.ts` hands the canvas to the wallpaper's worker (its code is inlined in the host's chunk, so there's no extra request). The worker loads its font, draws its sprite sheets, pre-warms and animates, all off the page's main thread.
2. It then `import()`s `src/start.tsx` (storage + React + dashboard, about 340 KB at 0.18.0; C7 measures what's in it). With the rain in its worker, the app starts as soon as it arrives (until 0.5.0 it waited for the rain's pre-warm on the same thread).

The pre-warm records the simulation into typed arrays and paints each visible glyph once: bright ones first (the canvas fades in then), then the faint rest and the heads' leftover glows during the fade.

Timings come from `npm run e2e:perf`. It simulates a 120 ms network delay and measures repeat opens through the service worker:

| | Normal CPU | 4× slower CPU |
|---|---|---|
| Rain | about 0.15 s | about 0.4 s |
| Dashboard | about 0.07 s | about 0.27 s |

A first visit: rain about 0.37 s, dashboard about 0.43 s (the test server's HTTP/1.1 limit of 6 connections delays the app's chunk; GitHub Pages serves HTTP/2).

`app:start`, `app:booted` and `app:ui` performance marks time the app's stages; the wallpaper's `rain-atlas` and `rain-prewarm` measures come from its worker into the page's timeline.

## The page
```
.wallpaper         fixed, z 0 (index.html): haze · canvas (screen-sized, drawn by the worker) · floor (the darkening toward the bottom)
<main.ui-layer>    fixed, z 1: HUD, NAV, the modules, toast. Fades out and goes inert in immersive mode
<SystemPanel>      modal dialog (S)
<ModuleSettings>   modal dialog (a module's ⋯ ▸ SETTINGS)
<Finder>           modal dialog (/)
```
**Immersive mode (F):**
- `toggleFullscreen()` calls the Fullscreen API.
- `useFullscreenSync()` copies `document.fullscreenElement` into `ui.immersive` on every `fullscreenchange`. Esc and the browser's own controls therefore stay in sync.
- While immersive, `useIdleCursor` hides a still pointer.

## Bookmarks
```
bridge/background.js ──(externally_connectable)──▶ src/bridge/client.ts ──▶ store/bookmarks.ts ──▶ app/Bookmarks.tsx
 chrome.bookmarks        hello · bar · port "changed"   useBridge (app/useBridge.ts)   status · bar          deck / CONNECT prompt
```
**The bridge.**
- It answers three messages:
  - `hello`: its version and `features` (`favicons`, `open`; bridge 1.1.0 and later);
  - `bar`: the dashboard's tree, built by `bridge/tree.js` `dashboardBar` and reduced to id, title, url and children, plus `roots` counts for SYSTEM. The tree is:
    - every bookmarks bar Chrome keeps, joined, account copy (`syncing`) first;
    - then Other bookmarks and Mobile bookmarks as folders, when they hold anything;
  - `open`: `ntp` or `bookmarks` opens Chrome's New Tab page or Bookmark manager in a new tab next to the dashboard. Only these two pages.
  - `ask`, `forget`, `go`: SWITCH TO OPEN TAB (1.3.0, below).
- **New Tab** (`bridge/newtab.js`): if a dashboard tab is open in the same window, the new tab switches to it and closes itself; otherwise it becomes the dashboard (`location.replace`). Finding dashboard tabs uses `host_permissions` for the dashboard's address, not the `tabs` permission. Chrome ignores a host permission's path, so this is all of `thedungeons2077.github.io` (checked in a probe, 2026-10-24).
- **SWITCH TO OPEN TAB** (1.3.0; `app/switchTab.ts`, `lib/switching.ts`):
  - **What's kept:** `prefs.switchTabs`, a sorted list of places (Chrome match patterns: a link's origin and its path up to the last `/`, then `*`). You turn a link's place on from its ⋯ in edit mode. A plain left click on any link under it (tile, folder row, QUICK LAUNCH, the finder, keys 1–9) sends `go` instead of opening a tab.
  - **`go {url, pattern}`:** `chrome.tabs.query({ url: pattern })` (the dashboard's window first, then the tab used last), then `tabs.update` + `windows.update`. With no such tab, `tabs.create` next to the dashboard. A site the bridge can't see returns tabs without addresses, so it never matches: a new tab. No answer: the page opens it itself (still within the click's activation).
  - **`ask {origin: https://host/*}`:** an allowed site answers `granted` at once (the dashboard's own site, so quest_log_desktop's links, always). Otherwise the bridge opens `grant.html` in a small window and answers `asking`. Only an extension's own page can call `chrome.permissions.request`, and only on a click, which is why the window exists. Its ALLOW / CANCEL goes to `background.js`, which posts `{type: 'granted', origin, granted}` on every dashboard port. The page adds the place only then: you can take longer than a message waits (3 s).
  - **`forget {origin}`:** gives the site back once no place needs it. The dashboard's own site can't be given back (Chrome keeps manifest permissions).
  - **Manifest:** `optional_host_permissions: https://*/*, http://*/*`. Nothing beyond the dashboard's site is granted until you say yes.
- **Site icons** load as `<img>` from `chrome-extension://<id>/_favicon/?pageUrl=…&size=16|32` (Chrome's icon cache). That needs the bridge's `favicon` permission, plus `web_accessible_resources` for the dashboard's origin.
- Over a long-lived port it posts `changed`, debounced by 150 ms.
- **Keep-alive:** while the dashboard is visible it pings over the port every 20 s, which keeps the extension worker awake, so changes always arrive. When hidden, the pings stop.
- **If the port closes:** the page reconnects, with back-off from 1 to 10 s, paused while hidden, and asks again. It also asks again whenever its window regains focus.
- **Id:** `mbjnlinjocmaalhodjhpkadlpifnelic`, fixed by the manifest's public `key`. The private key was never kept, since an unpacked extension doesn't need it.

**Which bar shows:**
1. The bridge's live bar.
2. While the bridge is first being asked, the cached bar.
3. With no bridge, the imported copy (`layout.bookmarks.imported`).
4. With none of these, the CONNECT prompt.

**Folders:** which are open is stored in `layout.bookmarks.open`, keyed by folder path (`lib/bookmarks.ts` `folderKey`), so the same folder matches across the live bar and an imported copy. A folder's contents are first rendered when it first opens. An open folder drops down in its own grid cell, one link per row.

**Finding (`/`, `app/Finder.tsx`):** a combobox over a listbox (`aria-activedescendant`).
- `lib/find.ts` `findEntries` lists every openable link in dashboard order, skipping hidden items and anything in a hidden folder. `search` scores each typed word: title start, word start, inside the title, host start, host, folder, then letters in order. Ties go to the shorter title, then dashboard order.
- Commands follow the links. Enter opens the chosen link in a new tab, or runs the command.
- `app/useShownBar.ts` picks the bar shown (live, cached or imported), for NAV and the finder alike.

**Arrow keys (`deck/useArrowNav.ts`):** from a tile, folder heading, link or area heading, ← / → go to the previous / next item in page order, ↑ / ↓ to the nearest item in the row above or below, Home / End to the first / last. Items inside folded areas or folders are skipped.

**Links:** only http(s) links are clickable, because Chrome blocks webpages from opening chrome://, file:// and javascript:. They open in a new tab (`target=_blank`, `rel=noopener noreferrer`), so the dashboard never navigates away and its animation is never caught frozen mid-handoff.

**`bookmarks.html` import:** `lib/bookmarks.ts` `parseBookmarksHtml` reads the Netscape export without a DOM and takes the folder marked `PERSONAL_TOOLBAR_FOLDER`.

## Arranging (edit mode)
- **`lib/arrange.ts`** (pure) holds your `Arrangement`: `order` (NAV), `areas` and `hidden`, plus the `Panels` places. Both are stored in the layout document (since schema 3), so backups and snapshots cover them.
- **An edit is an `EditShape`:** the arrangement, the panels and the modules (`store/edit.ts`). `withPlace(shape, id, place)` places any panel, NAV, the brand panel or a module, so the grips and drags share one path.
- **Item keys** are `l:<url>` (`#2`… for repeats) and `f:<folder path>`.
- **`arrange(bar, arrangement)`** works out NAV, the areas, the hidden items, and what folders leave out. Unplaced items follow Chrome's order (`mergeOrder`).
- **`store/edit.ts`:** `begin` takes a BEFORE EDIT snapshot. `apply` pushes an undo step and saves at once. `undoLast` / `revert` step back. `done` locks and snapshots.
- **`app/arrangeDrag.ts`:** pointer drags past a 5 px threshold. Targets are read from `data-drop-section`, `data-item-key`, `data-kind`, `data-section` and `data-area-id`; Esc cancels. Panels move live through CSS variables and are saved on drop.
- **Keyboard alternatives:** the ⋯ menus (`deck/ArrangeMenu.tsx`), ↑ / ↓ on area grips, and arrow keys on panel grips.
- **Glides (`deck/useFlip.ts`):** layout, bookmarks and edit store listeners note every item's position before React redraws. After the commit, moved items are animated from their old positions (Web Animations, `id: 'flip'`, transforms only). Positions are relative to NAV's scroller. A note older than 250 ms is discarded.
- **Feedback:**
  - `store/bookmarks.ts` `fresh` lights arrivals for 4 s.
  - `uiStore.announce` feeds a polite live region (`App.tsx` `Announcer`).
  - Drags dim their source (`data-drag-source`) and show `.drop-line` or `.drop-zone`.
- **Snapping** (0.14.0): a dropped panel settles against the window's edges (8 px in) or another panel's edge within 8 px, lined up or beside it with an 8 px gap (`lib/arrange.ts` `snapBox`, used on drop in `app/arrangeDrag.ts`; arrow-key nudges don't snap).
- **Panels** are placed with `left`/`top` from shares of the window, clamped on screen. There are no transforms, so text stays crisp, and narrow windows ignore the places.

## Modules
- **What they are:** panels you add, place and size yourself (SEARCH, QUICK LAUNCH, TIME, CLOCK). The brand panel is grouped with them as an optional panel: `panels.brandOff` (only written when true, no schema bump) hides it; + MODULE offers it back.
- **Drawn at MODULE SIZE (`prefs.moduleScale`, 0.7 until chosen: `MODULE_SCALE`):** a module's stored width is in its own sizes. `app/arrangeDrag.ts` `scaleOf` (UI SCALE's zoom × the module size) divides a drawn width by it when saving it (drag, resize, arrow keys). They're kept in `layout.modules` (schema 4: the 3 → 4 step adds an empty list), so saving, snapshots, backups and restore cover them.
- **A module's own sizes (0.19.0, schema 6):** `module.sizes` may hold its own `scale` (SIZE: how big it's drawn against the UI, the same measure as MODULE SIZE, in `MODULE_OWN_STEPS` 40–200%) and `textScale`. Each replaces the dashboard's for that module only (OWN), and a missing one follows the dashboard (DASHBOARD). A `scale` equal to the dashboard's value is still OWN.
  - **Applying them:** `app/modules/Modules.tsx` sets them on the module's frame as CSS variables: `--m` = `lib/modules.ts` `moduleScaleOf` (its own SIZE, else the dashboard's MODULE SIZE) and `--text-scale`. app.css then sizes it as usual, on top of #root's UI SCALE zoom.
  - **History:** 0.18.0 (schema 5, the 4 → 5 step changing nothing) had three own sizes, `uiScale`, `textScale` and `moduleScale`, drawn at MODULE SIZE × (its UI SCALE ÷ the dashboard's). Two knobs for one effect, so the 5 → 6 step (`lib/migrations.ts` `ownScale`) folds them into `scale` = that product, snapped, using the document's own prefs: a module stays as big on screen at the dashboard's UI SCALE. Fixture tests of real version-4 and version-5 layouts are in `src/__tests__/clock.test.ts`.
  - **Dragging:** `scaleOf` uses the same figure, so drags and resizes save the right width.
  - **Editing:** each module's ⋯ ▸ SETTINGS shows the three, with DASHBOARD to follow again.
- **`lib/modules.ts`** (pure) holds the list's rules: `newModule` at a free spot down the right-hand side, `addModule`, `placeModule`, `removeModule`, `setSettings`, and `normalizeModules`, which drops unknown kinds, bad ids and malformed entries one by one, never the whole layout. Ids are `m…`, so they can't be taken for `nav` or `brand`.
- **Each kind's rules** are their own pure files:
  - `lib/search.ts`: the engines, a custom address with `%s`, and `searchUrl` (the words URL-encoded). The page only opens the address.
  - `lib/launch.ts`: tiles (`cleanUrl` takes only http(s) addresses), add, move, remove, and `launchTargets` for keys 1–9 across modules.
  - `lib/time.ts`: countdowns counted in calendar days (UTC midnights, so clock changes don't matter), `clockText`, and `toolsOpen` (the timer and stopwatch fold, saved straight to the layout like a folder's, not an undo step).
- **The page:**
  - `app/modules/catalog.ts` names each kind and holds its file (`SearchModule`, `LaunchModule`, `TimeModule`, each exporting `Panel` and `Settings`). They load with the app: lazily, the bundler split their shared code into seven small chunks, and a first visit was ~130 ms slower.
  - `app/modules/Modules.tsx` draws the frames: grip, ⋯ (`PopupMenu`), resize edge, the kind's panel (inert while editing), and the SETTINGS dialog (`ui.moduleSettings`). Narrow windows (`useNarrow`) stack them inside NAV's scrolling area instead.
  - `app/modules/actions.ts` is what the rest of the page uses: the finder's web search, keys 1–9 (`useShortcuts`), and PIN TO QUICK LAUNCH from a bookmark's ⋯.
- **CLOCK** (0.18.0) is a big clock and the date. Its digits are sized from the module's width (a container query, capped so they never overflow), so its resize edge resizes the clock. It redraws once a second, or once a minute with seconds hidden, only while seen (`app/modules/useNow.ts`, shared with TIME).
- **TIME and the battery.** Nothing loops. The clock redraws once a second, the countdowns at midnight, and the timer and stopwatch only while they run with their fold open. All of it pauses while the tab is hidden or the page is immersive, and reads the clock afresh when it's seen again. A running timer has one timeout to its end, so its notice arrives even from the background.

## Storage and recovery
IndexedDB, database `cyberdeck_terminal`, store `kv`. quest_log_desktop shares the origin, so the name is this app's own. The keys:

| Key | Holds |
|---|---|
| `layout.v1` | The layout document (`lib/layout.ts`) |
| `meta.backup.v1` | Last export, reminder snooze, first run |
| `bookmarks.cache.v1` | The bridge's last bookmarks bar: a cache for an instant first draw. Not in the layout or backups |
| `snapshot.<ms>` | Automatic snapshots: `{ at, reason, summary, layout }` |
| `corrupt.<ms>` | Data that couldn't be read, kept rather than overwritten |

**Startup (`store/persist.ts` `boot`):**
1. Load the layout.
2. Migrate and validate it.
3. If it can't be read, copy it to `corrupt.*`, start fresh, and show a notice.
   - A layout from a newer version is copied but left in place.
4. Take a startup snapshot if the layout differs from the newest snapshot.

**Snapshots are indexed.** `snapshots.index.v1` lists each snapshot's time, reason, summary and content fingerprint (`layoutFingerprint`: a hash of the canonical JSON).
- Startup, the RESTORE list, the "has anything changed?" check and pruning all read only the index.
- A whole snapshot is read only to restore it.
- A missing or out-of-step index is rebuilt from the stored copies.

**Saving and snapshots (`store/layout.ts`):**
- Every change is saved at once.
- A snapshot follows once the layout has been still for 30 s.
- Import and restore snapshot the current layout first, so they can be undone.

**Keeping snapshots (`lib/snapshots.ts`):**
- The newest 20 are kept.
- So is the newest of each of the last 7 days.
- A copy identical to the newest snapshot is never stored.

**Backup files (`lib/backup.ts`):**
- Shape: `{ format: 'cyberdeck_terminal-backup', version: 1, exportedAt, app, layout }`.
- Import parses, migrates and validates, then shows a preview before anything is replaced.
- The reminder (`lib/reminder.ts`) offers EXPORT / LATER once the last export is older than the interval. It stays quiet while the layout still has nothing of its own.

## Wallpapers
The contract is `src/wallpaper/types.ts`: `create(canvas, { palette, glow, still, onReady })` → `{ resize(w, h, dpr, zoom), start, stop, setStill, setGlow, setPalette, destroy }`. A wallpaper runs in a worker on an OffscreenCanvas, or on the page if a worker can't, so its code may only use what both have: OffscreenCanvas, the font set, `requestAnimationFrame`. No DOM.

- The wallpaper's colours are its own palette (lib/palettes.ts), apart from the dashboard's. When it changes, `setWallpaperColors` sends the new colours over; the wallpaper redraws its sprites and carries on.
- Each wallpaper can have its own light layers in CSS: the host sets `data-wallpaper` on `.wallpaper`, and app.css styles its background, haze and floor per wallpaper.
- **Zoom** (`prefs.wallpaperZoom`: each wallpaper's own, by id, only where it isn't 100%; `lib/layout.ts` ZOOM_STEPS are Chrome's levels from 50% to 200%).
  - **How a wallpaper zooms.** It's part of the size: `resize(w, h, dpr, zoom)`. The rain, the neural net, DATA FLOW and MEGACITY lay themselves out with `zoomedSize` (MEGACITY's ledge keeps its place on the screen): for a screen 1/zoom as big, drawn zoom times as large, as browser zoom would for the wallpaper alone. The pixel ratio is capped first (the ratio in force: see Sharpness), then zoomed, so the canvas keeps its pixels at any zoom: sharp, never scaled up.
  - **VELOCITY** is laid out in shares of the screen, so `zoomedSize` would change nothing; it scales its sizes instead: the panels' widths and drift (not their lean: the slant stays), the streaks, the fine lines, and the flare with its arc, about the flare's corner.
  - **The host** keeps every wallpaper's zoom and a start-up hint (`cyberdeck_terminal:zoom`, a JSON map), so a wallpaper opens at its zoom before the layout is read; `setWallpaperZooms` resizes the running one when its zoom changes.
  - **The controls.** SYSTEM ▸ APPEARANCE ▸ ZOOM (− value + RESET), the keys + − 0 (`app/zoom.ts`; in fullscreen too) and three finder commands. A zoom step is a layout change, saved and backed up like the glow.
- **`host.ts`** (the page):
  - **The worker.** It transfers the canvas (`transferControlToOffscreen`) to `worker.ts` with the app's font URL, the palette, the glow, the size and the zoom, then forwards resize (with the zoom), start, stop, Reduce Motion and glow as messages. The worker answers `ready` (the canvas fades in), forwards the wallpaper's performance measures, and answers the tests' probes.
  - **The fallback.** If a canvas can't go to a worker, or the worker fails, the same wallpaper runs on the page, on a fresh canvas. Its engine (`registry.ts`) is loaded only then, so the page's own scripts don't carry it.
  - **The canvas is the size of the screen** (or the window, where that's bigger), not the window: resizing the window or going fullscreen doesn't touch it. Only a new screen size, zoom or pixel ratio resizes it (debounced by 150 ms). (0.15.1 sized it to the screen at the page's browser zoom; the user preferred the old behaviour, back in 0.15.2.)
  - **Chrome's zoom is cancelled for the wallpaper too** (0.17.1, with SYSTEM ▸ CHROME ZOOM on IGNORE, the default). `wantedSize` works the size out as at 100%: the window's CSS px times the zoom being cancelled (`src/scale.ts` `cancelledZoomNow`), and the pixel ratio divided by it. Chrome's `screen.width` doesn't follow its zoom. The canvas's CSS size is that size ÷ the zoom, so it still covers the window exactly. A wallpaper then looks the same at any Chrome zoom, and only SYSTEM ▸ ZOOM zooms it. `onBrowserZoom` resizes it at once when the zoom, or IGNORE/APPLY, changes. The browser walk checks it with a simulated 175%.
  - Visibility (stopped while the tab is hidden) and Reduce Motion (a still frame).
  - **The tests' probe**, `window.__cyberdeckRain`: `pixels()` (the share of the canvas that's lit, a fingerprint, and its size in pixels), `frames(ms)` (frame gaps and drawing time in the worker), `mode()` (`worker` or `page`), `zoom()` (the running wallpaper's), `sharpness()` (the ratio in force and the guard's verdict). The page can't read a canvas it handed to a worker.
- **MEGACITY** (`megacity/`) was the first in WebGL 2, because its city has tens of thousands of windows.
  - **One pass per pixel.** `city.ts` lays the city out once: per layer of towers, a skyline (per column, the top there and which tower it is), packed into a float texture. `shaders/city.frag` walks the layers near to far and stops at the first tower a pixel is inside. Its face, lit roof edge, edge strip and windows all come from the tower's seed, and the windows go on and off by the clock. Nothing is drawn twice, and nothing about the city is sent per frame.
  - **Its cache** (0.13.1). The city's clock only switches windows, so the city is drawn into a cache once a second (the clock in whole seconds) and copied each frame. A new city, size, palette or glow draws it again at once. On the phone that took a frame's graphics work from 5.09 ms to 0.93 ms (fluid_motion 0.7.0).
  - **Small draws on top.** Then the signs, haze patches, beacons and drones (`sim.ts`, a few kilobytes a frame), and the foreground (`city.ts` foreground: the railing and the ledge).
  - **Shared with fluid_motion.** Its shaders are fluid_motion's too (`assets/shaders/mc_*`, kept the same), and its layout is ported rule for rule (`lib/megacity`).
- **Sharpness** (0.14.0, `lib/sharpness.ts`).
  - **The cap.** The host passes each engine the pixel ratio in force: the screen's own, up to `SHARP_DPR` (3). Each engine's own `MAX_DPR` is that ceiling. Each wallpaper's safe cap (`catalog.ts` `safeDpr`: 2, VELOCITY 1.5, what it drew at before) applies once the guard has stepped back. On the page (no worker) it's always the safe cap.
  - **The guard.** Where full sharpness would draw more than the safe cap, the host waits `GUARD_SETTLE_MS` after `ready`, then reads the worker's frame ring (`stats` probe: each frame's start and drawing time, the last 512). If p95 drawing is over `GUARD_BUDGET_MS` (8), it steps back and resizes. Verdicts are a hint, `cyberdeck_terminal:sharp`. `retrySharpness` (SYSTEM's TRY AGAIN) forgets them. The browser tests set `cyberdeck_terminal:sharp-budget` to 0 to see it step back.
- **COPY DIAGNOSTICS** (`app/diagnostics.ts` gathers, `lib/diagnostics.ts` formats, tested): browser and OS (Client Hints), GPU (a throwaway WebGL context's renderer), screen and window, the wallpaper's sharpness and its last 3 s of frames (`wallpaperReport`), startup marks (`app:start`, `app:booted`, `app:ui`, `wallpaper:ready`), and the layout's counts. Never an address.
- **HORIZON** (`horizon/`) is WebGL 2 too, with a depth buffer.
  - **The sky** is per pixel (`shaders/sky.frag`): the haze, the glow and its core. It never changes, so it's drawn only when the size, palette or glow changes; the canvas keeps it (`preserveDrawingBuffer`).
  - **The land** (`land.ts`) is made once per layout size: a field 64 units deep cut into cells that follow the layout's height (1 unit at 1080 CSS px; smaller for a bigger layout, so more triangles zoomed out, as the other wallpapers' detail; 0.5 to 1.2), about 12 000 triangles at 1080 px, plus a far wall of haze that fills the band up to the horizon. So every pixel below the horizon is redrawn each frame (scissored to the bottom half), and the sky above is left alone. Each strip of triangles is placed by the shader at its distance from the camera now (`uCamZ`, the only per-frame number). A strip passing behind the near clip comes round at the far end, deep in the haze, so the land never ends and never pops. Strips are drawn nearest first (two ranges of the buffer), so the depth test drops hidden fragments early; the haze amount is per vertex, its colour only where there is haze.
  - **Edges** (0.17.4) come from each triangle's corner weights and their gradient's length (not `fwidth`, which over-reads slanted edges and draws them thinner, in steps), so every line is the same width at any distance and angle. The core is a soft bell; a wider glow (a Gaussian bloom and a long tail, its strength per GLOW level) sits round it. The far land fades into the same `haze()` the sky draws (one function, written into both shaders).
  - **No multisampling.** `antialias: true` smoothed the hills' outlines but made it laggy on the user's machine (0.17.4, off again in 0.17.5). The outlines a near hill draws over the land behind stay slightly stepped.
  - **Shared with fluid_motion** (its 0.8.0): its shaders are `assets/shaders/hz_*` there, byte for byte. The phone frames it through uniforms and its own mesh: smaller cells on an upright screen, strips far end first with no depth buffer, within a triangle budget (fluid_motion's ARCHITECTURE.md).
- **SUNSET** (`sunset/`) is WebGL 2, the lightest of them. It has no geometry, textures or depth buffer: two full-screen triangles' worth of per-pixel shader.
  - **The sky** (`shaders/sky.frag`: the sky, stars, striped sun, glow, scanlines) is drawn once per size, palette or zoom, and kept (`preserveDrawingBuffer`).
  - **Each frame** draws only the ground below the horizon (scissored, `shaders/ground.frag`). Each pixel finds the spot on the ground it sees, then its distance to the nearest grid line from the gradient's length (0.17.3), drawn as a soft bell with a Gaussian glow. The only per-frame input is how far the grid has come, wrapped after whole squares and whole wave cycles.
  - **The horizon** (0.17.2–0.17.3). Far off, where squares are a few px, the lines fade into the dark ground with a little of their average light (they once piled up into a bright band). Below the horizon, the ground melts into the sky's own colour (the same gradient and sun glow `sky.frag` draws just above, `uMeltH`, 5% of the height), so there's no line between them.
  - **Shared with fluid_motion** (its 0.8.0): `assets/shaders/ss_*`, byte for byte. `sky.frag` asks for `precision highp int` because its star hash multiplies 32-bit numbers, which phone GPUs would otherwise do at medium precision.
- **`catalog.ts`** names the wallpapers for the page (SYSTEM's list, checking ids); **`registry.ts`** holds their engines (the worker, or the fallback).

**To add a wallpaper:** create a folder under `src/wallpaper/`, export a `Wallpaper` from it, add it to `WALLPAPERS` in `registry.ts`, and its name card to `catalog.ts`. Its `id` is stored in layouts and backups, so it must never change once released.

### Canvas probe
- The tests' probe reads 2D or WebGL canvases alike (`wallpaper/probe.ts`).

### Data flow (`src/wallpaper/data-flow/`)
- **`params.ts`** holds every tunable number. There's no reference image: the look is a printed circuit board's (DESIGN.md).
- **`board.ts`** lays out the board, pure and seeded (unit tested; fluid_motion's Kotlin port lays out the same way).
  - **Grid.** Points are `PITCH` apart, a few past every edge of the screen. Traces run in the eight directions 45° apart.
  - **Chips.** The main chip sits a little right of the middle. Side chips are spread out (each the farthest of several tries from the others). Each chip has a clear ring with pins every 2 points.
  - **Buses.** Neighbouring pins run out together on one route (`plan`). Before a 90° bend the outer traces run on further, so a bus bends like a ribbon. A trace blocked at once isn't laid.
  - **Loose traces** fill the rest, some as small buses from a row of vias, until `COVERAGE` of the screen's points carry one.
  - **Spacing.** Traces never cross or touch: one trace a point, no diagonal between two taken points, and one free point beside every trace.
- **`engine.ts`** draws the still board once into a layer of its own (per size, palette and glow): the dot grid, the traces (with the glow level's soft glow), vias, pads and chips.
  - **Each frame** copies that layer and adds the light ('lighter'): packets running along the traces (a halo, a tail brightening in six slices, a glowing head sprite), the afterglow of traces that just carried one, vias flashing, chips glowing as data arrives. It's a few hundred small strokes, whatever the screen size.
  - **Rate and opening.** It draws on every frame the screen shows. 2.5 s of packets are simulated before the first frame.
- Colours come from the wallpaper's palette (`flowTones`): warm traces and packets from `--text-dim` / `--accent`, cool ones from `--cool`. The glow round the main chip is CSS.

### Velocity (`src/wallpaper/velocity/`)
- **`engine.ts`** redraws everything each frame, additively ('lighter') on a clear canvas: each panel is one rectangle drawn through a skew (its lean), with a soft gradient and a striation pattern; streaks are thin gradient rectangles; the flare a radial gradient and an arc. Up to about 72 frames a second at up to 1.5 device px per CSS px.
- Colours from the wallpaper's palette (`tones`): pale light from `--cool`, red from `--accent`.

### Neural net (`src/wallpaper/neural-net/`)
- **`params.ts`** holds every tunable number, matched to its reference (DESIGN.md).
- **`engine.ts`** builds a scene per screen size (`scene`): node homes (a scatter plus clusters, past the screen's edges), links (`linkNodes`: each node's picks from its nearer neighbours, so some reach far). Each frame it redraws everything, cheaply:
  - one stroke per link at its exact opacity (plus a wide soft pass for glow), so links fade smoothly as they stretch; it draws on every frame the screen shows (no frame-rate cap);
  - nodes and signals as copies of small glow sprites, one per colour step (`sprites`, rebuilt when the palette, glow or pixel ratio changes);
  - colour by place along a diagonal (`shade`): `--cool`, `--text-bright`, `--accent`. The big glow behind is CSS (app.css `.wallpaper[data-wallpaper='neural-net']`).
- No pre-warm: the first frame is the whole picture.

### Matrix rain (`src/wallpaper/matrix-rain/`)
- **Its light layers are CSS** (app.css), around the canvas: `.wallpaper-haze` behind it (a faint accent wash) and `.wallpaper-floor` over it (the darkening toward the bottom). Since 0.17.6 both span the full height along smooth curves with a stop every 10%: the haze is (1 + cos πt) / 2 of 7% accent, the floor t³ of the background. Earlier the floor covered only the bottom 16%, and the haze had corners at 55% and 95%; their edges read as lines across the screen. fluid_motion's `rain_composite.frag` works out the same curves per pixel.
- **`params.ts`** holds every tunable number, matched to the reference wallpaper.
- **`glyphAtlas.ts`** pre-draws every glyph, with its glow, once per layer into a sprite sheet (an OffscreenCanvas).
  - Its rows are HEAD, BODY and DIM, plus ERASE (each glyph's bare shape, a touch bolder) and HALO (a head with its shape cut out: the glow a head leaves behind). ERASE and HALO aren't needed for the first paint, so they're drawn right after it (`finish`).
  - Each row's slots are the cell plus as far as that row's glow reaches (`GLOW_REACH`), so big head glows aren't cut off and the much more frequent body copies stay small.
  - **The glow** (SYSTEM ▸ WALLPAPER ▸ GLOW, `prefs.rainGlow`): `params.ts` `GLOW` sets the glow colour's strength and the heads' and bodies' blur for LOW, MEDIUM, HIGH (default) and MAX. A change rebuilds the sheets; the rain carries on, so the new glow rains in.
  - Katakana are used only if a system font can draw them (`canDraw`).
- **`engine.ts`** never repaints the whole canvas. Each frame it does three things:
  1. fades one set of interleaved 2 px stripes, a twelfth of the screen. Each pixel is still faded once per 0.2 s, but no frame fades everything, so there's no whole-screen dimming pulse and no expensive frame. The fills are plain solid rectangles, the cheap path on both GPU and CPU canvases (a pattern fill measured many times slower on a CPU canvas);
  2. copies in the glyphs that drops moved onto;
  3. re-rolls a few glyphs inside trails (the flicker).
- **Changing a glyph in place** (a head turning into body, the flicker) first cuts the old glyph out by its own shape (the ERASE row, `destination-out`), never by clearing its cell, which punched dark boxes into the glow around it. `glyphAt` keeps each cell's glyph for that. A head's glow stays behind as it moves on, so lit trails glow as streaks; the pre-warm records where (`halo`) and paints it (the HALO row).
- **Drops:** each column of each layer has one drop slot. A drop falls to a random depth, then waits at the top. The wait sets the layer's occupancy.
- **Startup:** 18 s of rain are simulated before the canvas is shown, so it opens full.
  - Only glyphs still at least 5% bright are painted.
  - In the worker the work runs in big slices (`PREWARM_WORKER_BUDGET_MS`), stopping once after the bright glyphs so that frame shows. On the page (the fallback) it's 16 ms per frame, then 6 ms once the canvas shows, so the dashboard isn't kept waiting.
  - `onReady` fades the canvas in after the bright part.
- **Resize** (rare: the canvas is screen-sized): the drawn pixels are copied across and columns are added or removed.

`npm run e2e:motion` measures the rain's frame gaps and drawing time in its worker, the page's main-thread script time (normal CPU and 4× slower), the sprite sheets and pre-warm, the worst main-thread stall while loading, and the frame just after a resize. Compare a change against a copy of the old `dist/` with `MOTION_DIST` (older builds are measured by the page's frames).
