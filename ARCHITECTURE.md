# Architecture

## Layers
| Folder | What | May import |
|---|---|---|
| `src/lib/` | Pure rules: the layout document, migrations, backup files, snapshot keeping, the reminder | nothing outside `lib` |
| `src/store/` | State and storage: `persist.ts` (startup), `layout.ts` (layout store), `ui.ts` (screen state), `idbKV.ts` / `kv.ts` (storage) | `lib` |
| `src/wallpaper/` | Animated wallpapers on a canvas: `host.ts` owns the canvas and runs the wallpaper in `worker.ts`; `catalog.ts` names them, `registry.ts` holds their engines | `lib` (ids and glow levels only) |
| `src/bridge/` | `client.ts`: messaging with the bridge extension (Chrome's externally_connectable API) | `lib` |
| `bridge/` | The **CYBERDECK BRIDGE** extension itself (MV3, plain JS), zipped into the build as `cyberdeck-bridge.zip` | nothing |
| `src/app/` | React UI: `App`, `Hud`, `SystemPanel`, `Dialog`, `Toast`, shortcuts, fullscreen; the deck in `Bookmarks.tsx` + `deck/`; `arrangeDrag.ts`, `panels.tsx` | everything |

## Palettes
- **`src/lib/palettes.ts`** (pure): the palettes, each a set of base colours keyed by token (`PALETTE_TOKENS`), plus WCAG contrast maths for the test that holds every palette to the colour rule.
- **Two palettes, chosen apart:** the dashboard's (`prefs.palette`) and the wallpaper's (`prefs.wallpaperPalette`; a layout from before 0.6.1 starts it from the dashboard's).
- **`src/palette.ts`** puts the dashboard's palette on the page: it sets the base tokens on `<html>` (inline custom properties) and remembers the choice in localStorage (`cyberdeck_terminal:palette`), so `main.tsx` can apply it before the wallpaper reads the colours, and a non-default palette never flashes green first.
- **theme.css** mixes every other colour from the base tokens (`color-mix`), so a palette recolours everything.
- **The wallpaper's palette** is the host's (`setWallpaperColors`): it sets the same base tokens on the `.wallpaper` element itself, so the wallpaper's CSS layers (which use only base tokens, mixed in place) take its colours while the page keeps the dashboard's; it sends the colours to the engine, and keeps its own start-up hint (`cyberdeck_terminal:wallpaper-palette`).
- Both are in the layout (no schema bump: missing ones get PHOSPHOR, or the dashboard's), so backups and snapshots keep them.

## Service worker
`sw.js` is generated by `vite.config.ts`.
- **The page is served from its cache**: no network round trip before it can start.
- **The browser checks `sw.js` on every open.** A new build installs in the background, fetching every file with `cache: 'reload'` so it never stores a stale copy, and shows from the next open.
- **The previous build's cache is kept**, so a page still open on it can load its remaining chunks.
- **Cache names** are `cyberdeck_terminal-<build time>-<hash>`, so they sort by age.

## Startup
`index.html` holds the wallpaper's canvas as plain HTML, and lists every file the start needs (fonts, the first chunks, and the app's chunk as a `modulepreload`), so they're all fetched at once.
1. `src/main.tsx`, the first chunk (about 1 KB, plus the host's 16 KB), starts the wallpaper at once: `wallpaper/host.ts` hands the canvas to the wallpaper's worker (its code is inlined in the host's chunk, so there's no extra request). The worker loads its font, draws its sprite sheets, pre-warms and animates, all off the page's main thread.
2. It then `import()`s `src/start.tsx` (storage + React + dashboard, about 290 KB). With the rain in its worker, the app starts as soon as it arrives (until 0.5.0 it waited for the rain's pre-warm on the same thread).

The pre-warm records the simulation into typed arrays and paints each visible glyph once: bright ones first (the canvas fades in then), then the faint rest and the heads' leftover glows during the fade.

Timings come from `npm run e2e:perf`. It simulates a 120 ms network delay and measures repeat opens through the service worker:

| | Normal CPU | 4× slower CPU |
|---|---|---|
| Rain | about 0.15 s | about 0.4 s |
| Dashboard | about 0.07 s | about 0.27 s |

A first visit: rain about 0.37 s, dashboard about 0.43 s (the test server's HTTP/1.1 limit of 6 connections delays the app's chunk; GitHub Pages serves HTTP/2).

`app:start`, `app:booted` and `app:ui` performance marks time the app's stages; the wallpaper's `rain-atlas` and `rain-prewarm` measures come from its worker into the page's timeline.

## The page
```
.wallpaper         fixed, z 0 (index.html): haze · canvas (screen-sized, drawn by the worker) · fade to black at the bottom
<main.ui-layer>    fixed, z 1: HUD, NAV, toast. Fades out and goes inert in immersive mode
<SystemPanel>      modal dialog (S)
<Finder>           modal dialog (/)
```
**Immersive mode (F):**
- `toggleFullscreen()` calls the Fullscreen API.
- `useFullscreenSync()` copies `document.fullscreenElement` into `ui.immersive` on every `fullscreenchange`. Esc and the browser's own controls therefore stay in sync.
- While immersive, `useIdleCursor` hides a still pointer.

## Bookmarks
```
bridge/background.js ──(externally_connectable)──▶ src/bridge/client.ts ──▶ store/bookmarks.ts ──▶ app/Bookmarks.tsx
 chrome.bookmarks        hello · bar · port "changed"   useBridge (app/useBridge.ts)   status · bar          deck / CONNECT prompt
```
**The bridge.**
- It answers three messages:
  - `hello`: its version and `features` (`favicons`, `open`; bridge 1.1.0 and later);
  - `bar`: the dashboard's tree, built by `bridge/tree.js` `dashboardBar` and reduced to id, title, url and children, plus `roots` counts for SYSTEM. The tree is:
    - every bookmarks bar Chrome keeps, joined, account copy (`syncing`) first;
    - then Other bookmarks and Mobile bookmarks as folders, when they hold anything;
  - `open`: `ntp` or `bookmarks` opens Chrome's New Tab page or Bookmark manager in a new tab next to the dashboard. Only these two pages.
- **New Tab** (`bridge/newtab.js`): if a dashboard tab is open in the same window, the new tab switches to it and closes itself; otherwise it becomes the dashboard (`location.replace`). Finding dashboard tabs uses `host_permissions` for the dashboard's address only, not the `tabs` permission.
- **Site icons** load as `<img>` from `chrome-extension://<id>/_favicon/?pageUrl=…&size=16|32` (Chrome's icon cache). That needs the bridge's `favicon` permission, plus `web_accessible_resources` for the dashboard's origin.
- Over a long-lived port it posts `changed`, debounced by 150 ms.
- **Keep-alive:** while the dashboard is visible it pings over the port every 20 s, which keeps the extension worker awake, so changes always arrive. When hidden, the pings stop.
- **If the port closes:** the page reconnects, with back-off from 1 to 10 s, paused while hidden, and asks again. It also asks again whenever its window regains focus.
- **Id:** `mbjnlinjocmaalhodjhpkadlpifnelic`, fixed by the manifest's public `key`. The private key was never kept, since an unpacked extension doesn't need it.

**Which bar shows:**
1. The bridge's live bar.
2. While the bridge is first being asked, the cached bar.
3. With no bridge, the imported copy (`layout.bookmarks.imported`).
4. With none of these, the CONNECT prompt.

**Folders:** which are open is stored in `layout.bookmarks.open`, keyed by folder path (`lib/bookmarks.ts` `folderKey`), so the same folder matches across the live bar and an imported copy. A folder's contents are first rendered when it first opens. An open folder drops down in its own grid cell, one link per row.

**Finding (`/`, `app/Finder.tsx`):** a combobox over a listbox (`aria-activedescendant`).
- `lib/find.ts` `findEntries` lists every openable link in dashboard order, skipping hidden items and anything in a hidden folder. `search` scores each typed word: title start, word start, inside the title, host start, host, folder, then letters in order. Ties go to the shorter title, then dashboard order.
- Commands follow the links. Enter opens the chosen link in a new tab, or runs the command.
- `app/useShownBar.ts` picks the bar shown (live, cached or imported), for NAV and the finder alike.

**Arrow keys (`deck/useArrowNav.ts`):** from a tile, folder heading, link or area heading, ← / → go to the previous / next item in page order, ↑ / ↓ to the nearest item in the row above or below, Home / End to the first / last. Items inside folded areas or folders are skipped.

**Links:** only http(s) links are clickable, because Chrome blocks webpages from opening chrome://, file:// and javascript:. They open in a new tab (`target=_blank`, `rel=noopener noreferrer`), so the dashboard never navigates away and its animation is never caught frozen mid-handoff.

**`bookmarks.html` import:** `lib/bookmarks.ts` `parseBookmarksHtml` reads the Netscape export without a DOM and takes the folder marked `PERSONAL_TOOLBAR_FOLDER`.

## Arranging (edit mode)
- **`lib/arrange.ts`** (pure) holds your `Arrangement`: `order` (NAV), `areas` and `hidden`, plus the `Panels` places. Both are stored in the layout document (schema 3), so backups and snapshots cover them.
- **Item keys** are `l:<url>` (`#2`… for repeats) and `f:<folder path>`.
- **`arrange(bar, arrangement)`** works out NAV, the areas, the hidden items, and what folders leave out. Unplaced items follow Chrome's order (`mergeOrder`).
- **`store/edit.ts`:** `begin` takes a BEFORE EDIT snapshot. `apply` pushes an undo step and saves at once. `undoLast` / `revert` step back. `done` locks and snapshots.
- **`app/arrangeDrag.ts`:** pointer drags past a 5 px threshold. Targets are read from `data-drop-section`, `data-item-key`, `data-kind`, `data-section` and `data-area-id`; Esc cancels. Panels move live through CSS variables and are saved on drop.
- **Keyboard alternatives:** the ⋯ menus (`deck/ArrangeMenu.tsx`), ↑ / ↓ on area grips, and arrow keys on panel grips.
- **Glides (`deck/useFlip.ts`):** layout, bookmarks and edit store listeners note every item's position before React redraws. After the commit, moved items are animated from their old positions (Web Animations, `id: 'flip'`, transforms only). Positions are relative to NAV's scroller. A note older than 250 ms is discarded.
- **Feedback:**
  - `store/bookmarks.ts` `fresh` lights arrivals for 4 s.
  - `uiStore.announce` feeds a polite live region (`App.tsx` `Announcer`).
  - Drags dim their source (`data-drag-source`) and show `.drop-line` or `.drop-zone`.
- **Panels** are placed with `left`/`top` from shares of the window, clamped on screen. There are no transforms, so text stays crisp, and narrow windows ignore the places.

## Storage and recovery
IndexedDB, database `cyberdeck_terminal`, store `kv`. quest_log_desktop shares the origin, so the name is this app's own. The keys:

| Key | Holds |
|---|---|
| `layout.v1` | The layout document (`lib/layout.ts`) |
| `meta.backup.v1` | Last export, reminder snooze, first run |
| `bookmarks.cache.v1` | The bridge's last bookmarks bar: a cache for an instant first draw. Not in the layout or backups |
| `snapshot.<ms>` | Automatic snapshots: `{ at, reason, summary, layout }` |
| `corrupt.<ms>` | Data that couldn't be read, kept rather than overwritten |

**Startup (`store/persist.ts` `boot`):**
1. Load the layout.
2. Migrate and validate it.
3. If it can't be read, copy it to `corrupt.*`, start fresh, and show a notice.
   - A layout from a newer version is copied but left in place.
4. Take a startup snapshot if the layout differs from the newest snapshot.

**Snapshots are indexed.** `snapshots.index.v1` lists each snapshot's time, reason, summary and content fingerprint (`layoutFingerprint`: a hash of the canonical JSON).
- Startup, the RESTORE list, the "has anything changed?" check and pruning all read only the index.
- A whole snapshot is read only to restore it.
- A missing or out-of-step index is rebuilt from the stored copies.

**Saving and snapshots (`store/layout.ts`):**
- Every change is saved at once.
- A snapshot follows once the layout has been still for 30 s.
- Import and restore snapshot the current layout first, so they can be undone.

**Keeping snapshots (`lib/snapshots.ts`):**
- The newest 20 are kept.
- So is the newest of each of the last 7 days.
- A copy identical to the newest snapshot is never stored.

**Backup files (`lib/backup.ts`):**
- Shape: `{ format: 'cyberdeck_terminal-backup', version: 1, exportedAt, app, layout }`.
- Import parses, migrates and validates, then shows a preview before anything is replaced.
- The reminder (`lib/reminder.ts`) offers EXPORT / LATER once the last export is older than the interval. It stays quiet while the layout still has nothing of its own.

## Wallpapers
The contract is `src/wallpaper/types.ts`: `create(canvas, { palette, glow, still, onReady })` → `{ resize, start, stop, setStill, setGlow, setPalette, destroy }`. A wallpaper runs in a worker on an OffscreenCanvas, or on the page if a worker can't, so its code may only use what both have: OffscreenCanvas, the font set, `requestAnimationFrame`. No DOM.

- The wallpaper's colours are its own palette (lib/palettes.ts), apart from the dashboard's. When it changes, `setWallpaperColors` sends the new colours over; the wallpaper redraws its sprites and carries on.
- Each wallpaper can have its own light layers in CSS: the host sets `data-wallpaper` on `.wallpaper`, and app.css styles its background, haze and floor per wallpaper.
- **`host.ts`** (the page):
  - **The worker.** It transfers the canvas (`transferControlToOffscreen`) to `worker.ts` with the app's font URL, the palette, the glow and the size, then forwards resize, start, stop, Reduce Motion and glow as messages. The worker answers `ready` (the canvas fades in), forwards the wallpaper's performance measures, and answers the tests' probes.
  - **The fallback.** If a canvas can't go to a worker, or the worker fails, the same wallpaper runs on the page, on a fresh canvas. Its engine (`registry.ts`) is loaded only then, so the page's own scripts don't carry it.
  - **The canvas is the size of the screen** (or the window, where that's bigger), not the window: resizing the window or going fullscreen doesn't touch it. Only a new screen size, zoom or pixel ratio resizes it (debounced by 150 ms).
  - Visibility (stopped while the tab is hidden) and Reduce Motion (a still frame).
  - **The tests' probe**, `window.__cyberdeckRain`: `pixels()` (the share of the canvas that's lit, and a fingerprint), `frames(ms)` (frame gaps and drawing time in the worker), `mode()` (`worker` or `page`). The page can't read a canvas it handed to a worker.
- **`catalog.ts`** names the wallpapers for the page (SYSTEM's list, checking ids); **`registry.ts`** holds their engines (the worker, or the fallback).

**To add a wallpaper:** create a folder under `src/wallpaper/`, export a `Wallpaper` from it, add it to `WALLPAPERS` in `registry.ts`, and its name card to `catalog.ts`. Its `id` is stored in layouts and backups, so it must never change once released.

### Canvas probe
- The tests' probe reads 2D or WebGL canvases alike (`wallpaper/probe.ts`).

### Data flow (`src/wallpaper/data-flow/`)
- **`params.ts`** holds every tunable number. There's no reference image: the look is a printed circuit board's (DESIGN.md).
- **`board.ts`** lays out the board, pure and seeded (unit tested; fluid_motion's Kotlin port lays out the same way).
  - **Grid.** Points are `PITCH` apart, a few past every edge of the screen. Traces run in the eight directions 45° apart.
  - **Chips.** The main chip sits a little right of the middle. Side chips are spread out (each the farthest of several tries from the others). Each chip has a clear ring with pins every 2 points.
  - **Buses.** Neighbouring pins run out together on one route (`plan`). Before a 90° bend the outer traces run on further, so a bus bends like a ribbon. A trace blocked at once isn't laid.
  - **Loose traces** fill the rest, some as small buses from a row of vias, until `COVERAGE` of the screen's points carry one.
  - **Spacing.** Traces never cross or touch: one trace a point, no diagonal between two taken points, and one free point beside every trace.
- **`engine.ts`** draws the still board once into a layer of its own (per size, palette and glow): the dot grid, the traces (with the glow level's soft glow), vias, pads and chips.
  - **Each frame** copies that layer and adds the light ('lighter'): packets running along the traces (a halo, a tail brightening in six slices, a glowing head sprite), the afterglow of traces that just carried one, vias flashing, chips glowing as data arrives. It's a few hundred small strokes, whatever the screen size.
  - **Rate and opening.** It draws on every frame the screen shows. 2.5 s of packets are simulated before the first frame.
- Colours come from the wallpaper's palette (`flowTones`): warm traces and packets from `--text-dim` / `--accent`, cool ones from `--cool`. The glow round the main chip is CSS.

### Velocity (`src/wallpaper/velocity/`)
- **`engine.ts`** redraws everything each frame, additively ('lighter') on a clear canvas: each panel is one rectangle drawn through a skew (its lean), with a soft gradient and a striation pattern; streaks are thin gradient rectangles; the flare a radial gradient and an arc. Up to about 72 frames a second at up to 1.5 device px per CSS px.
- Colours from the wallpaper's palette (`tones`): pale light from `--cool`, red from `--accent`.

### Neural net (`src/wallpaper/neural-net/`)
- **`params.ts`** holds every tunable number, matched to its reference (DESIGN.md).
- **`engine.ts`** builds a scene per screen size (`scene`): node homes (a scatter plus clusters, past the screen's edges), links (`linkNodes`: each node's picks from its nearer neighbours, so some reach far), and bokeh. Each frame it redraws everything, cheaply:
  - one stroke per link at its exact opacity (plus a wide soft pass for glow), so links fade smoothly as they stretch; it draws on every frame the screen shows (no frame-rate cap);
  - nodes, signals and bokeh as copies of small glow sprites, one per colour step (`sprites`, rebuilt when the palette, glow or pixel ratio changes);
  - colour by place along a diagonal (`shade`): `--cool`, `--text-bright`, `--accent`. The big glow behind is CSS (app.css `.wallpaper[data-wallpaper='neural-net']`).
- No pre-warm: the first frame is the whole picture.

### Matrix rain (`src/wallpaper/matrix-rain/`)
- **`params.ts`** holds every tunable number, matched to the reference wallpaper.
- **`glyphAtlas.ts`** pre-draws every glyph, with its glow, once per layer into a sprite sheet (an OffscreenCanvas).
  - Its rows are HEAD, BODY and DIM, plus ERASE (each glyph's bare shape, a touch bolder) and HALO (a head with its shape cut out: the glow a head leaves behind). ERASE and HALO aren't needed for the first paint, so they're drawn right after it (`finish`).
  - Each row's slots are the cell plus as far as that row's glow reaches (`GLOW_REACH`), so big head glows aren't cut off and the much more frequent body copies stay small.
  - **The glow** (SYSTEM ▸ WALLPAPER ▸ GLOW, `prefs.rainGlow`): `params.ts` `GLOW` sets the glow colour's strength and the heads' and bodies' blur for LOW, MEDIUM, HIGH (default) and MAX. A change rebuilds the sheets; the rain carries on, so the new glow rains in.
  - Katakana are used only if a system font can draw them (`canDraw`).
- **`engine.ts`** never repaints the whole canvas. Each frame it does three things:
  1. fades one set of interleaved 2 px stripes, a twelfth of the screen. Each pixel is still faded once per 0.2 s, but no frame fades everything, so there's no whole-screen dimming pulse and no expensive frame. The fills are plain solid rectangles, the cheap path on both GPU and CPU canvases (a pattern fill measured many times slower on a CPU canvas);
  2. copies in the glyphs that drops moved onto;
  3. re-rolls a few glyphs inside trails (the flicker).
- **Changing a glyph in place** (a head turning into body, the flicker) first cuts the old glyph out by its own shape (the ERASE row, `destination-out`), never by clearing its cell, which punched dark boxes into the glow around it. `glyphAt` keeps each cell's glyph for that. A head's glow stays behind as it moves on, so lit trails glow as streaks; the pre-warm records where (`halo`) and paints it (the HALO row).
- **Drops:** each column of each layer has one drop slot. A drop falls to a random depth, then waits at the top. The wait sets the layer's occupancy.
- **Startup:** 18 s of rain are simulated before the canvas is shown, so it opens full.
  - Only glyphs still at least 5% bright are painted.
  - In the worker the work runs in big slices (`PREWARM_WORKER_BUDGET_MS`), stopping once after the bright glyphs so that frame shows. On the page (the fallback) it's 16 ms per frame, then 6 ms once the canvas shows, so the dashboard isn't kept waiting.
  - `onReady` fades the canvas in after the bright part.
- **Resize** (rare: the canvas is screen-sized): the drawn pixels are copied across and columns are added or removed.

`npm run e2e:motion` measures the rain's frame gaps and drawing time in its worker, the page's main-thread script time (normal CPU and 4× slower), the sprite sheets and pre-warm, the worst main-thread stall while loading, and the frame just after a resize. Compare a change against a copy of the old `dist/` with `MOTION_DIST` (older builds are measured by the page's frames).
